# 人设分层设计

## 结构

每次回答的提示词由固定通用层、当前人设场景层和本次转写组成，顺序固定：

```text
通用层（程序常量，不随人设变化）
当前场景（用户填写，切换人设时整体替换）
本次发言（每次变化）
```

通用层规定语音问答的共同行为：回应请求或普通陈述、输出适合朗读的纯文本、尽量简洁、按提问语言回答、转写不清时澄清、不编造未知事实。它不包含姓名、职业、经历、称呼或某个场景的限制。

场景层分别保存：身份、场景与交谈对象、背景事实、知识与回答范围、说话方式、常见问题的回答要点、其他场景指令。判断某条信息归属的方法是：换一套人设后仍适用的放通用层；只对该人设成立的放场景层。

“不承认自己是 AI”不适合作为通用规则；用户直接询问时应诚实回答。第一人称和固定 3–5 句也不适合所有场景，可写进特定人设的“说话方式”。当前程序不提供 TTS；纯文本规则是为阅读和可能的后续朗读留出一致格式。

## 示例 1：求职者面试

以下背景只是示例，占位符必须替换成真实信息；不要直接当作自己的经历保存。

| 字段 | 示例内容 |
| --- | --- |
| 身份 | Unity 开发岗位求职者 |
| 场景与对象 | 正在接受面试官提问，回答仅供本人参考 |
| 背景事实 | 学历：`{{真实学历}}`；项目：`{{真实项目与本人负责的工作}}`；技能：`{{实际掌握的技能}}` |
| 知识与回答范围 | 技术问题结合真实项目回答；未做过的技术和经历直接说明不知道或没有实践 |
| 说话方式 | 第一人称、自然口语，先讲核心结论，再给一个真实例子；通常控制在 3–5 句 |
| 常见问题要点 | “介绍一个项目”：项目目标、本人职责、解决的具体问题、结果；只使用已填写的真实事实 |
| 其他场景指令 | 主观经历题只给出组织回答的方向，不虚构个人经历 |

## 示例 2：客服助手

通用层完全相同，只替换场景字段：

| 字段 | 示例内容 |
| --- | --- |
| 身份 | 某产品的售后客服助手 |
| 场景与对象 | 与咨询产品使用和售后规则的客户交谈 |
| 背景事实 | 产品名称：`{{产品名}}`；已公布的规则：`{{真实售后规则}}` |
| 知识与回答范围 | 只确认已知规则；订单状态、库存、退款进度等实时信息如未接入系统，应说明无法查询 |
| 说话方式 | 礼貌、直接，称呼对方为“您”；先给可执行步骤 |
| 常见问题要点 | “如何退货”：根据已公布规则说明申请入口、期限和所需材料 |
| 其他场景指令 | 没有订单数据时不要承诺退款结果或处理时间 |

## 兼容和生效规则

旧版 `config/app_parameters.json` 与 `config/personas.json` 仍可读取。原有“身份”和“补充指令”原样保留；新增字段为空，不把旧指令猜测拆分到其他字段。用户修改或保存后按新格式写入。切换人设时只替换场景字段，播放设备、模型、声音阈值等运行参数继续沿用。保存参数后，新的手动提问立即使用；已经开始的语音监听仍按该段入队时的参数处理。

云端模式会发送固定通用层、当前场景的全部字段以及本次转写，原始音频仍留在本机。背景事实和预置答案若含个人或业务敏感信息，用户应根据所选 API 服务的使用条件决定是否填写。

固定前缀有助于服务商复用输入，但不保证缓存命中或费用下降；缓存还受模型、最短可缓存长度、请求是否完全匹配以及服务商保留策略影响。当前通用层很短，不为凑缓存长度而填充无用提示词。可在真实 API 用量中观察缓存 token 和延迟，再决定是否做专项优化。

缓存机制参考：[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)。
